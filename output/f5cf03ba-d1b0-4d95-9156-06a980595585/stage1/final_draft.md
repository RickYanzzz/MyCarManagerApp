## 2 产品概述

### 2.1 行业背景与痛点

汽车维修、保养、洗车美容等门店普遍为小微经营主体，经营高度依赖人工经验与纸质/微信记录，存在以下典型痛点：

| 序号 | 行业痛点 | 具体表现 | 对经营的影响 |
| --- | --- | --- | --- |
| 1 | 开单效率低 | 手写工单、口头记项目，车牌、项目、价格靠手工誊抄 | 客户等待时间长，高峰期易拥堵 |
| 2 | 车辆信息分散 | 车主、联系方式、车架号、保险到期等信息散落于纸质台账或微信 | 车辆档案无法沉淀，复购与召回无从下手 |
| 3 | 结算方式混乱 | 现金、微信、赠送、挂账等多种方式混用，无统一记录 | 账目不清，欠款难以追踪，易产生坏账 |
| 4 | 经营数据缺失 | 当日营收靠人工统计或凭感觉 | 无法掌握门店真实经营状况，决策缺乏依据 |
| 5 | 门店与员工管理弱 | 账号无归属、无权限边界、数据无隔离 | 数据安全与责任划分无法保障 |
| 6 | 工具门槛高 | 传统 PC 端管理系统需购置电脑、部署安装、专人学习 | 小门店用不起来、用不下去 |

### 2.2 产品定位

**智慧车店**是一款面向汽车维修/保养门店（修理厂、快修店、洗车美容店）的**移动端经营管理工具**，帮助门店老板和员工**用手机**完成开单、施工、结算、车辆档案管理等日常工作。

产品定位要点：

| 维度 | 定位描述 |
| --- | --- |
| 产品形态 | 移动端应用，一部手机即可经营 |
| 目标场景 | 门店日常「接车—开单—施工—结算」经营闭环 |
| 交付方式 | 一套代码多端发布，覆盖 Android App、iOS App、微信小程序、H5 |
| 数据组织 | 以「企业/门店」为数据隔离单位的多租户 SaaS 结构 |
| 使用门槛 | 面向一线员工与门店老板，操作路径短、无需专业培训 |

### 2.3 目标用户

| 用户类型 | 用户描述 | 核心诉求 |
| --- | --- | --- |
| 门店老板 | 门店经营者与最终决策人，关注营收与账目 | 实时掌握今日收入、订单与欠款情况，随时随地把控经营 |
| 门店员工（前台/技师） | 一线接车与施工人员 | 快速录入车牌与项目、快速开单、快速结算，不耽误客户 |
| 门店管理者（店长/财务） | 负责订单与账目核对 | 订单分类清晰、挂账可跟踪、车辆档案可查 |

> 注：上述角色在当前版本统一使用「员工账号（user）」登录，账号归属于某个企业（enterprise）；角色与权限的精细划分属**规划中**能力（见 5.6.5）。

### 2.4 核心价值主张

| 价值主张 | 支撑能力 | 用户收益 |
| --- | --- | --- |
| 开单更快 | 可视化车牌键盘 + 车牌拍照 OCR 自动识别 | 车牌录入从「手动输入」变为「选择或拍照」，显著缩短开单时间 |
| 流程更顺 | 消费开单 → 施工单 → 结算的连贯链路 | 一单到底，不换系统、不重复录入 |
| 账目更清 | 多付款方式 + 部分付款 + 挂账机制 | 未付清订单自动进入挂账订单，欠款有据可查 |
| 数据更实 | 今日收入实时统计（口径明确） | 打开首页即见当天真实入账金额 |
| 档案更全 | 结构化的车辆档案（车牌、车主、车架号、保险到期等） | 客户与车辆资产沉淀在门店，而非员工个人 |
| 数据更安全 | 以 enterprise 为隔离单位的多租户模型 | 门店之间数据天然隔离，互不可见 |

### 2.5 技术架构概览

| 层次 | 技术选型 | 说明 |
| --- | --- | --- |
| 前端框架 | uni-app + Vue2 跨端框架 | 一套代码同时发布多端 |
| 客户端形态 | Android App、iOS App、微信小程序、H5 | 多端一致的操作体验 |
| 状态管理 | Vuex + 本地存储 | 维护登录态与全局用户/企业信息 |
| 后端运行时 | uniCloud（阿里云）云函数 | 承载全部业务逻辑与接口 |
| 数据存储 | uniCloud 云数据库 | 存储 8 个业务集合（见第 7 章） |
| 第三方能力 | 百度车牌识别 API | 支撑车牌拍照 OCR 自动识别 |
| 租户模型 | 以 enterprise（企业/门店）为数据隔离单位 | 员工账号归属于企业，数据按 `enterpriseId` 隔离 |

技术架构带来的产品约束：

1. **多端一致性**：所有功能需在 App、小程序、H5 上保持一致的信息结构与操作路径。
2. **数据隔离前置**：所有涉及业务数据的操作，必须携带并校验 `enterpriseId`。
3. **能力按端降级**：拍照 OCR 等依赖设备能力的功能，需在无相机权限或识别失败时提供可用的降级路径（手动输入）。

## 3 用户与使用场景

### 3.1 用户角色画像

| 角色 | 典型画像 | 关注指标 | 使用频次 | 当前版本核心使用功能 |
| --- | --- | --- | --- | --- |
| 门店老板 | 40 岁左右，自有门店，手机操作熟练度中等 | 今日收入、订单量、挂账金额 | 每日多次（碎片化查看） | 首页工作台、订单管理、车辆档案 |
| 前台/接车员 | 20–35 岁，负责接车与开单，操作需快 | 开单速度、结算是否正确 | 每单必用，高频 | 消费开单（车牌录入、OCR、添加项目、结算） |
| 技师 | 负责施工，关注本单要做什么 | 施工项目是否清晰 | 每单必用 | 施工单（查看与添加消费项目） |
| 店长/财务 | 负责对账与欠款跟踪 | 挂账订单、入账订单 | 每日（对账时集中使用） | 订单管理（临时/挂账/入账三类） |

### 3.2 典型业务场景

**场景一：日常接车开单（主线场景）**

客户驾车到店，前台接车。前台打开「消费开单」，通过可视化车牌键盘选择省份简称与字母数字逐位录入车牌；或将摄像头对准车牌拍照，由 OCR 自动识别并回填车牌号。若为军牌、港澳牌等特殊车牌，则改用手动输入方式。车牌录入完成后进入施工单页面。

**场景二：施工中增补项目**

车辆进入施工环节后，技师或前台在「消费开单—施工中」页面查看已添加项目，并按需从门店预设的「套餐/服务项目」中选择新项目加入本单，形成本次消费明细。

**场景三：结算与部分付款**

施工完成后发起结算，在结算页选择付款方式（微信、现金、赠送等多种）。若客户本次只支付部分金额，系统支持部分付款，未付清部分形成挂账，订单进入「挂账订单」列表，后续可继续跟进收款。

**场景四：订单跟进与补收款**

店长在「挂账订单」列表中筛出未付清订单，查看订单详情，进入对应施工单继续操作或完成尾款结算。结算付清后，订单状态变为已入账，进入「入账订单」列表。

**场景五：车辆档案沉淀与查询**

前台为到店车辆新增档案，记录车牌号、车主姓名、联系方式、车辆类型、车辆品牌、发动机号、车架号、保险到期日及备注说明。后续同车到店时可直接查询到历史信息，减少重复询问。

**场景六：经营者查看今日收入**

门店老板随时打开首页工作台，查看「今日收入」实时统计值，了解当天真实入账情况；同时可通过业务功能宫格入口快速跳转到消费开单、各类订单列表。

## 5 详细功能需求

### 5.1 登录鉴权【已实现】

#### 5.1.1 功能描述

为门店员工提供基于「手机号 + 密码」的账号登录能力，并在登录过程中完成账号可用性校验与企业归属信息加载，登录成功后维持登录态，支持主动退出。

#### 5.1.2 交互流程

| 步骤 | 操作角色 | 操作内容 | 系统响应 |
| --- | --- | --- | --- |
| 1 | 员工 | 打开应用，进入登录页 | 展示手机号输入框、密码输入框、登录按钮 |
| 2 | 员工 | 输入手机号与密码，点击「登录」 | 校验输入完整性，发起登录请求 |
| 3 | 系统 | 校验账号是否存在 | 不存在 → 提示账号或密码错误 |
| 4 | 系统 | 校验账号启用/禁用状态 | 被禁用 → 提示「账号已被禁用，请联系管理员」 |
| 5 | 系统 | 校验通过后加载所属企业信息 | 返回企业名称、地址、收据抬头、联系电话等 |
| 6 | 系统 | 保存登录态 | 写入本地存储并同步至 Vuex |
| 7 | 系统 | 跳转首页工作台 | 进入默认首页 |

#### 5.1.3 业务规则

| 序号 | 规则 |
| --- | --- |
| R1 | 登录凭证为「手机号 + 密码」，手机号即账号（对应用户名） |
| R2 | 账号存在 `isEnable`（是否启用）标识；禁用账号登录时必须拦截并提示联系管理员 |
| R3 | 登录成功后必须加载该账号所属企业（enterprise）信息，作为后续业务数据的租户上下文 |
| R4 | 登录态需双写：本地存储 + Vuex，保证应用重启后仍保持登录 |
| R5 | 提供退出登录能力，退出时需清理登录态与企业上下文 |

#### 5.1.4 字段说明

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| 手机号 | 字符串 | 是 | 登录账号，对应用户名 |
| 密码 | 字符串 | 是 | 登录凭证 |
| 是否启用 | 布尔 | 是（系统） | 账号可登录标识，禁用则拦截登录 |
| 所属企业 ID | 字符串 | 是（系统） | 租户标识，登录后写入会话上下文 |

| 序号 | 功能项 | 说明 | 状态 |

| 2 | 今日支出 | 支出展示位（当前为占位） | 【已实现（占位）】 |
| 3 | 业务功能宫格 | 提供消费开单、临时订单、挂账订单、入账订单四个主入口 | 【已实现】 |

#### 5.2.3 交互流程

| 步骤 | 触发 | 系统行为 |
| --- | --- | --- |

| 2 | 进入首页 | 执行 App 版本检查 |
| 3 | 版本检查 | 有新版本 → 弹出升级提示；无新版本 → 静默通过 |
| 4 | 点击宫格入口 | 跳转对应业务页面（消费开单 / 临时订单 / 挂账订单 / 入账订单） |

#### 5.2.4 业务规则

| 序号 | 规则 |
| --- | --- |
| R1 | 今日收入口径：**当天状态 = 已入账（订单状态 2）的订单中，付款类型不等于「赠送」的金额之和**（详见 10.2 指标口径说明） |
| R2 | 今日收入需实时统计，不依赖离线缓存值 |
| R3 | 「今日支出」为占位项，本期不参与统计与计算 |
| R4 | 业务功能宫格固定为四个入口：消费开单、临时订单、挂账订单、入账订单 |

### 5.3 消费开单【已实现】（产品主线）

消费开单是产品的核心链路，包含「车牌录入 → 施工单 → 添加消费项目 → 结算」四个环节。

#### 5.3.1 车牌录入

**功能描述**

在开单起始页完成车牌号的录入，提供三种互补的录入方式，覆盖常规车牌与特殊车牌。

| 录入方式 | 适用场景 | 说明 |
| --- | --- | --- |
| 可视化车牌键盘 | 常规车牌快速录入 | 省份简称 + 字母数字逐位选择，避免手输错误 |
| 车牌拍照 OCR | 常规车牌极速录入 | 调用百度车牌识别 API 自动识别并回填 |
| 手动输入 | 特殊车牌 | 军牌、港澳牌等无法用标准键盘表达的车牌 |

**交互流程**

| 步骤 | 操作 | 系统响应 |
| --- | --- | --- |
| 1 | 进入消费开单页 | 展示车牌录入区域与录入方式入口 |
| 2 | 选择可视化车牌键盘 | 展示省份简称选择区与字母数字选择区，逐位点选 |
| 3 | 逐位完成选择 | 车牌号实时拼装展示，可回退修改 |
| 4 | 或点击拍照识别 | 唤起相机/相册，选图后上传识别 |
| 5 | OCR 返回结果 | 成功 → 自动回填车牌号；失败 → 明确提示识别失败，引导手动录入 |
| 6 | 或选择特殊车牌手动输入 | 提供文本输入，登记车牌输入类型 |
| 7 | 确认车牌 | 进入「消费开单—施工中」页面（施工单） |

**业务规则**

| 序号 | 规则 |
| --- | --- |
| R1 | 车牌号为本单必填项，未完成录入不可进入施工单 |
| R2 | 车牌需记录「车牌输入类型」，区分可视化键盘、OCR 识别、手动输入来源 |
| R3 | OCR 识别失败必须给出明确提示，不得静默失败 |
| R4 | 特殊车牌（军牌/港澳牌等）走手动输入，不受标准键盘规则限制 |

#### 5.3.2 车牌 OCR 拍照识别

**功能描述**

通过拍照或从相册选图，调用百度车牌识别 API 自动识别车牌号并回填至车牌输入框。

**交互流程**

| 步骤 | 操作 | 系统响应 |
| --- | --- | --- |
| 1 | 点击「拍照识别」 | 弹出拍照 / 相册选择 |
| 2 | 拍照或选择图片 | 上传图片并发起识别请求 |
| 3 | 识别处理中 | 展示加载状态 |
| 4a | 识别成功 | 自动回填车牌号到输入框，用户可核对修改 |
| 4b | 识别失败 | 明确提示识别失败原因，引导用户改用可视化键盘或手动输入 |
| 5 | 用户确认 | 按 5.3.1 流程继续开单 |

**业务规则**

| 序号 | 规则 |
| --- | --- |
| R1 | 识别能力由第三方 API（百度车牌识别）提供，须处理网络异常、返回无车牌、置信度不足等异常 |
| R2 | 识别结果为「回填建议值」，用户可手动修正 |
| R3 | 识别失败不得阻断开单流程，必须提供可用的手动录入降级路径 |

#### 5.3.3 施工单（billingDetail）

**功能描述**

进入「消费开单—施工中」页面（施工单，billingDetail）后，可查看本单已添加的消费项目，继续添加项目，并在我完成后发起结算。

**交互流程**

| 步骤 | 操作 | 系统响应 |
| --- | --- | --- |
| 1 | 车牌录入完成 | 创建/进入施工单页面，展示本单车牌与已添加项目列表 |
| 2 | 查看已添加项目 | 展示项目名称、价格与小计 |
| 3 | 点击「添加项目」 | 进入添加消费项目页面（见 5.3.4） |
| 4 | 选择项目后返回 | 施工单项目列表刷新，金额重新计算 |
| 5 | 点击「发起结算」 | 进入结算页（见 5.3.5） |

**业务规则**

| 序号 | 规则 |
| --- | --- |
| R1 | 施工单以订单为载体，记录用户 ID、企业 ID、车辆 ID、下单时间与订单状态 |
| R2 | 施工单持续可编辑，直至完成结算 |
| R3 | 已添加项目以「消费明细（purchased_goods）」持久化，支持多次追加 |

#### 5.3.4 添加消费项目（addConsumePro）

**功能描述**

从门店预设的「套餐/服务项目」中勾选项目加入本单，形成本单消费明细。

**交互流程**

| 步骤 | 操作 | 系统响应 |
| --- | --- | --- |
| 1 | 在施工单点击「添加项目」 | 进入添加消费项目页，加载门店预设套餐/服务项目列表 |
| 2 | 浏览项目列表 | 展示套餐名称、价格，热门项目突出显示 |
| 3 | 勾选项目 | 标记已选，展示已选合计 |
| 4 | 确认添加 | 写入本单消费明细，返回施工单并刷新金额 |

**业务规则**

| 序号 | 规则 |
| --- | --- |
| R1 | 可选项目来源于当前企业（门店）预设的商品/套餐集合（goods），按 `enterpriseId` 隔离 |

#### 5.3.5 结算（PayController）

**功能描述**

施工完成后发起结算，选择付款方式并确认支付金额，支持多种付款方式、部分付款与挂账。

**交互流程**

| 步骤 | 操作 | 系统响应 |
| --- | --- | --- |
| 1 | 施工单点击「发起结算」 | 进入结算页，展示本单应付金额 |
| 2 | 选择付款方式 | 展示付款方式列表（微信、现金、赠送等多种） |
| 3 | 输入本次支付金额 | 校验金额合法性；支持小于应付金额 |
| 4 | 确认支付 | 生成付款记录（pay_infos），计算本单已付与未付金额 |
| 5a | 全额付清 | 订单状态置为已入账（2），进入入账订单列表 |
| 5b | 部分付款/未付清 | 订单状态置为挂账（1），进入挂账订单列表，未付部分可后续补收 |

**业务规则**

| 序号 | 规则 |
| --- | --- |
| R1 | 付款方式至少覆盖微信、现金、赠送等多种类型，付款记录需保存付款方式名称、付款类型、付款金额 |
| R2 | 系统支持部分付款：单次支付金额可小于应付金额 |
| R3 | 未付清订单必须置为挂账状态（1），保证欠款可追溯 |
| R4 | 付款类型为「赠送」的金额不计入今日收入统计（见 R5 与 10.2） |
| R5 | 结算完成后，订单状态不得回退；如需继续收款，应通过挂账订单进入施工单追加付款记录 |

**字段说明**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| 付款方式名称 | 字符串 | 是 | 如微信、现金、赠送 |
| 付款类型 | 字符串 | 是 | 用于区分是否计入收入（赠送不计入） |
| 付款金额 | 数值 | 是 | 本次支付金额 |
| 订单 ID | 字符串 | 是 | 关联所属订单 |
| 车辆 ID | 字符串 | 是 | 关联所属车辆 |

## 6 核心业务流程

### 6.1 全链路流程总览

消费开单全链路（本产品主线）：

```
车牌录入（键盘 / OCR / 手动）
        ↓
进入施工单（billingDetail，订单状态 0 临时订单）
        ↓
添加消费项目（addConsumePro，写入消费明细）
        ↓
发起结算（PayController，选择付款方式、输入支付金额）
        ↓
   ┌────────────┴────────────┐
全额付清                    未付清
   ↓                          ↓
订单状态 = 2（已付）        订单状态 = 1（挂账）
进入「入账订单」            进入「挂账订单」→ 后续补收尾款 → 状态 2
   ↓
计入「今日收入」统计（付款类型 ≠ 赠送）
```

### 6.2 流程环节说明

| 环节 | 输入 | 处理 | 输出 | 涉及数据 |
| --- | --- | --- | --- | --- |
| 车牌录入 | 车牌号（键盘/OCR/手动） | 校验必填，记录输入类型 | 车牌号 + 输入类型 | car_info |
| 建立施工单 | 车牌号、登录用户、企业 | 创建订单，记录下单时间，状态置 0 | 订单记录 | order |
| 添加消费项目 | 门店预设套餐/服务项目 | 选择项目、写入消费明细 | 本单项目清单与金额 | goods、purchased_goods |
| 发起结算 | 应付金额、付款方式、支付金额 | 生成付款记录，判定是否付清 | 付款记录 + 新订单状态 | pay_infos、order |
| 挂账跟进 | 挂账订单 | 进入施工单追加付款 | 付款记录、状态变更 | pay_infos、order |
| 收入统计 | 当日已入账订单与付款记录 | 按口径求和 | 今日收入数值 | order、pay_infos、todays_income |

### 6.3 订单状态流转

| 当前状态 | 触发动作 | 目标状态 | 说明 |
| --- | --- | --- | --- |
| 无（新建） | 车牌录入完成并建立施工单 | 0 临时订单 | 施工进行中 |
| 0 临时订单 | 结算且全额付清 | 2 已付订单 | 直接入账 |
| 0 临时订单 | 结算但未付清（部分付款） | 1 挂账订单 | 形成欠款 |
| 1 挂账订单 | 补收尾款且付清 | 2 已付订单 | 欠款结清 |
| 0 / 1 / 2 | 删除订单 | —（记录移除） | 需二次确认 |

> 规则：订单状态单向推进，已入账（2）的订单不可回退为挂账（1）或临时（0）。

### 6.4 异常与分支流程

| 异常/分支 | 触发条件 | 处理策略 |
| --- | --- | --- |
| OCR 识别失败 | 图片无车牌 / 置信度不足 / 网络异常 | 明确提示失败，引导使用可视化键盘或手动输入 |
| 无相机权限 | 用户拒绝相机权限 | 提供相册选图或手动输入降级路径 |
| 账号被禁用 | 管理员禁用账号 | 登录拦截并提示联系管理员 |
| 部分付款 | 支付金额小于应付金额 | 订单转入挂账状态，保留未付金额 |
| 结算后需继续收款 | 客户后续补齐欠款 | 从挂账订单进入施工单，追加付款记录 |
| 企业信息加载失败 | 登录请求企业信息异常 | 需保证登录态一致性，异常时提示并允许重试 |

## 8 非功能需求

### 8.1 性能需求

| 序号 | 指标项 | 目标要求 |
| --- | --- | --- |
| P1 | 登录响应 | 正常网络下登录完成（含企业信息加载）应快速返回，避免用户长时间等待 |
| P2 | 开单关键路径 | 车牌录入、添加项目、结算等高频操作应即时响应，操作后立即给出反馈 |
| P3 | 今日收入统计 | 首页进入后应快速完成统计与渲染，不阻塞页面展示 |
| P4 | 列表加载 | 订单列表、车辆档案列表需支持分页/增量加载，避免一次性全量拉取 |
| P5 | OCR 识别 | 图片上传与识别过程需提供加载状态，超时或失败必须给出明确提示 |

### 8.2 安全需求

| 序号 | 指标项 | 要求 |
| --- | --- | --- |
| S1 | 身份认证 | 未登录不可访问业务页面；账号禁用时禁止登录 |
| S2 | 登录态管理 | 登录态需持久化并支持清理，退出登录需清除本地与全局状态 |
| S3 | 数据隔离 | 所有业务查询与写入必须校验 `enterpriseId`，防止越权访问他店数据 |
| S4 | 敏感信息 | 密码等敏感字段不得在前端明文暴露；手机号、联系方式等需按需展示 |
| S5 | 权限边界 | 账号与权限精细化管理为规划能力，本期依靠账号归属企业实现基础隔离 |

### 10.2 指标口径说明

| 指标 | 口径定义 | 数据来源 |
| --- | --- | --- |
| 今日收入 | 当天状态 = 已入账（订单状态 2）的订单中，付款类型**不等于**「赠送」的付款金额之和 | order（状态过滤）+ pay_infos（金额、付款类型过滤） |
| 今日支出 | 本期为展示占位，未定义统计口径 | — |
| 挂账金额 | 挂账订单（状态 1）中未付清的金额 | order + pay_infos |

**口径要点说明：**

1. **时间口径**：以「当天」为统计窗口，即当日产生的已入账订单。
2. **状态口径**：仅统计状态为已入账（2）的订单，挂账（1）与临时（0）不计入。
3. **付款类型口径**：付款类型为「赠送」的金额**不计入**今日收入，避免虚增营收。
4. **实现要求**：该口径在系统内应集中定义、统一使用，避免出现首页统计与其他位置口径不一致。
